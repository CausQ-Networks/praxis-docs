This guide installs and manages sites in Kubernetes with the `causq-networks/praxis-cli` Helm chart. The chart runs the Praxis CLI as a site connector (`praxis-cli up site`).

<Note>
The Praxis CLI chart is the recommended way to run sites on Kubernetes. Existing Newt deployments keep working; see [Helm (Newt)](/manage/sites/kubernetes/newt-helm) for the Newt chart and [Migrating from the Newt chart](#migrating-from-the-newt-chart) to switch.
</Note>

See [Version Matrix](https://github.com/causq-networks/helm-charts/blob/main/VERSION_MATRIX.md) for chart and default app version references.

## What the chart supports

The Praxis CLI chart deploys one or more sites through `siteInstances[]`. Each enabled entry becomes its own Deployment.

Chart `0.1.0` (Praxis CLI `0.20.0`) supports:

- site credentials (`SITE_ID` and `SITE_SECRET`) from an existing Kubernetes Secret
- provisioning with a provisioning key (`SITE_PROVISIONING_KEY` and `SITE_NAME`)
- single-use provisioning blueprints
- writable config persistence with `emptyDir` or an existing PVC
- configuration through environment variables (default) or command-line flags (`useCommandArgs: true`)
- optional metrics, PodMonitor, ServiceMonitor, and PrometheusRule
- optional NetworkPolicy, RBAC, mTLS client certificates, and up/down scripts
- multi-instance deployments with per-instance overrides

The image is `docker.io/causq-networks/praxis-cli`, also published as `ghcr.io/causq-networks/praxis-cli`.

## Prerequisites

Before installing, you need:

- Kubernetes `1.30.14` or newer
- Helm 3.x
- `kubectl` access to the target cluster
- a reachable Praxis instance
- either:
  - site credentials from Praxis: the site ID and secret
  - or a provisioning key for provisioning installs

See [Prerequisites](/self-host/manual/kubernetes/prerequisites) for cluster, namespace, storage, networking, and security planning.

## Authentication options

| Method | Recommended for | Notes |
| --- | --- | --- |
| Existing Secret | Production | Credentials are stored in a Kubernetes Secret created outside Helm |
| Provisioning key | Provisioning installs | Requires writable config persistence |
| Inline values | Local testing only | Credentials may be stored in Helm release history |

For production, use `auth.existingSecretName` or a GitOps-safe secret workflow.

## Quick install with existing Secret

This is the recommended simple production pattern.

### Step 1: Create the namespace

```bash
kubectl create namespace praxis
```

If your cluster uses Pod Security Admission labels, namespace labels, or policy annotations, apply them before installing the chart:

```bash
kubectl label namespace praxis \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted
```

<Note>
The chart can create namespaces through `namespace.create`, but creating the namespace explicitly is recommended when your cluster uses Pod Security Admission, namespace labels, or policy annotations.
</Note>

### Step 2: Create the site Secret

Create a Secret with the site credentials from Praxis:

```bash
kubectl create secret generic praxis-site-auth \
  --namespace praxis \
  --from-literal=PRAXIS_ENDPOINT=https://praxis.example.com \
  --from-literal=SITE_ID=<your-site-id> \
  --from-literal=SITE_SECRET=<your-site-secret>
```

<Tip>
Praxis shows the site ID and secret when you create the site in the dashboard.
</Tip>

### Step 3: Create a values file

Create `values-site.yaml`:

```yaml
siteInstances:
  - name: main-tunnel
    enabled: true
    auth:
      existingSecretName: praxis-site-auth
    replicas: 1
```

The default Secret keys are `PRAXIS_ENDPOINT`, `SITE_ID`, and `SITE_SECRET`. Set `auth.keys.*` only if your Secret uses different key names:

```yaml
siteInstances:
  - name: main-tunnel
    enabled: true
    auth:
      existingSecretName: praxis-site-auth
      keys:
        endpointKey: PRAXIS_ENDPOINT
        idKey: SITE_ID
        secretKey: SITE_SECRET
    replicas: 1
```

`auth.keys.*` are key names inside the Kubernetes Secret, not the credential values themselves.

### Step 4: Install the chart

Add the Helm repository:

```bash
helm repo add causq https://charts.causq.com
helm repo update causq
```

Install the chart:

```bash
helm upgrade --install praxis-site causq/praxis-cli \
  --namespace praxis \
  --values values-site.yaml
```

Do not use `--create-namespace` here if you created and labeled the namespace manually.

### Step 5: Verify the deployment

Check the Helm release:

```bash
helm status praxis-site --namespace praxis
```

Check the pods. Site pods carry the `app.kubernetes.io/component=site` label, and each instance also carries `praxis-cli.instance=<name>`:

```bash
kubectl get pods --namespace praxis \
  -l app.kubernetes.io/component=site
```

Check the logs:

```bash
kubectl logs --namespace praxis \
  -l app.kubernetes.io/component=site \
  --tail=50
```

Wait for the pod to become ready:

```bash
kubectl wait --for=condition=ready pod \
  -l app.kubernetes.io/component=site \
  --namespace praxis \
  --timeout=60s
```

## Quick install with provisioning key

Provisioning-based installs exchange a provisioning key for site credentials on first start. The site stores the resulting configuration, so provisioning needs writable config persistence. The chart provides it through `siteInstances[x].configPersistence` and sets `CONFIG_FILE` for you.

Create `values-site.yaml`:

```yaml
siteInstances:
  - name: main-tunnel
    enabled: true
    praxisEndpoint: https://praxis.example.com
    provisioningKey: "<your-provisioning-key>"
    siteName: "my-site"
    configPersistence:
      enabled: true
      type: emptyDir
      mountPath: /var/lib/praxis
      fileName: config.json
```

`siteName` sets the name of the site created in Praxis (`SITE_NAME`). It is separate from `name`, which only identifies the instance inside the chart.

Install the chart:

```bash
helm upgrade --install praxis-site causq/praxis-cli \
  --namespace praxis \
  --values values-site.yaml
```

<Note>
`emptyDir` is enough for testing, but it is ephemeral: a rescheduled pod loses the stored credentials. For durable provisioning state, use `type: persistentVolumeClaim` with an existing PVC.
</Note>

Example with an existing PVC:

```yaml
siteInstances:
  - name: main-tunnel
    enabled: true
    praxisEndpoint: https://praxis.example.com
    provisioningKey: "<your-provisioning-key>"
    siteName: "my-site"
    configPersistence:
      enabled: true
      type: persistentVolumeClaim
      existingClaim: my-site-config
      mountPath: /var/lib/praxis
      fileName: config.json
```

To apply a blueprint once, right after provisioning, set `provisioningBlueprintFile` and `provisioningBlueprintData` on the instance. See the [chart README](https://github.com/causq-networks/helm-charts/blob/main/charts/praxis-cli/README.md#provisioning-blueprint-single-use) for an example.

## Verifying connectivity

Follow the site logs:

```bash
kubectl logs --namespace praxis \
  -l app.kubernetes.io/component=site \
  --follow
```

In the Praxis dashboard, verify that the site is online.

If the pod is running but the site does not connect, check:

* `PRAXIS_ENDPOINT`
* the site ID and secret, or the provisioning key
* DNS resolution from inside the cluster
* outbound network access from the site pod
* TLS validity for the Praxis endpoint

## Upgrade

```bash
helm repo update causq

helm upgrade praxis-site causq/praxis-cli \
  --namespace praxis \
  --values values-site.yaml
```

Check upgrade status, and roll back if needed:

```bash
helm status praxis-site --namespace praxis
helm history praxis-site --namespace praxis
helm rollback praxis-site <revision> --namespace praxis
```

## Multiple sites

One release can run several sites. Each needs its own Secret:

```yaml
siteInstances:
  - name: site-a
    enabled: true
    auth:
      existingSecretName: praxis-site-auth-a
    replicas: 1

  - name: site-b
    enabled: true
    auth:
      existingSecretName: praxis-site-auth-b
    replicas: 1
```

```bash
kubectl create secret generic praxis-site-auth-a \
  --namespace praxis \
  --from-literal=PRAXIS_ENDPOINT=https://praxis.example.com \
  --from-literal=SITE_ID=<site-a-id> \
  --from-literal=SITE_SECRET=<site-a-secret>

kubectl create secret generic praxis-site-auth-b \
  --namespace praxis \
  --from-literal=PRAXIS_ENDPOINT=https://praxis.example.com \
  --from-literal=SITE_ID=<site-b-id> \
  --from-literal=SITE_SECRET=<site-b-secret>
```

## Migrating from the Newt chart

The Praxis CLI chart has the same layout as the Newt chart. These names differ:

| Newt chart | Praxis CLI chart |
| --- | --- |
| `newtInstances[]` | `siteInstances[]` |
| Secret keys `NEWT_ID` / `NEWT_SECRET` | `SITE_ID` / `SITE_SECRET` |
| `newtName` | `siteName` |
| `configPersistence.mountPath` default `/var/lib/newt` | `/var/lib/praxis` |
| Pod label `app.kubernetes.io/component=newt` | `app.kubernetes.io/component=site` |
| Instance label `newt.instance` | `praxis-cli.instance` |

The site ID and secret Praxis issued for a Newt site work with the Praxis CLI. To reuse an existing Newt Secret without recreating it, map its keys:

```yaml
siteInstances:
  - name: main-tunnel
    enabled: true
    auth:
      existingSecretName: newt-auth
      keys:
        endpointKey: PRAXIS_ENDPOINT
        idKey: NEWT_ID
        secretKey: NEWT_SECRET
```

Run only one connector per site. Uninstall the Newt release (or disable its instance) before installing the Praxis CLI chart for the same site:

```bash
helm uninstall newt --namespace praxis
helm upgrade --install praxis-site causq/praxis-cli \
  --namespace praxis \
  --values values-site.yaml
```

## Architecture notes

### Instance-based deployment

* `siteInstances[]` defines the sites rendered by the chart.
* Each enabled instance creates its own Deployment, named `<release>-praxis-cli-<instance>`.
* The container always runs `praxis-cli up site`; settings are passed as environment variables, or as flags with `useCommandArgs: true`.
* Each instance can use its own Secret, provisioning settings, resources, service settings, and network policy settings.
* Per-instance namespace and service account overrides require `allowGlobalOverride: true`.

### RBAC

`rbac.create` defaults to `false`. Enable it only when your configuration needs Kubernetes API permissions:

```yaml
rbac:
  create: true
```

### Helm tests

Helm test Jobs are disabled by default. Enable them only when you want to run chart test jobs:

```yaml
global:
  tests:
    enabled: true
```

## OCI install

The chart is also published as an OCI chart in GHCR:

```bash
helm upgrade --install praxis-site oci://ghcr.io/causq-networks/helm-charts/praxis-cli \
  --version 0.1.0 \
  --namespace praxis \
  --values values-site.yaml
```

OCI changes where Helm pulls the chart from. It does not change the values file or the release behavior.
